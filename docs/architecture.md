# Architecture

**Distributed AI Software Development Platform** — team6. Version for Sprint 1 (27 September 2026).
Sections marked *(planned)* describe the target design for later sprints; they are proposals the team refines at each Sprint Planning.

## 2. Components

### 2.1 Master (`master/`)

A FastAPI application packaged as a Docker image.

| Module | Responsibility |
|---|---|
| `app.py` | Wires the routers, serves the UI, `/health`, `/api/master/status` |
| `agents_api.py` | `POST /api/agents/register` (token-protected), `GET /api/agents` |
| `projects_api.py` | Create / list / read / re-analyse / delete projects; runs the analysis as a background task, one at a time |
| `decompose.py` | Requirements analysis with the master's model and deterministic task-graph construction |
| `llm.py` | Client for the master's local Ollama (`/api/chat` with JSON schema, `num_ctx`, `think: false`) |
| `extract.py` | Text extraction from PDF, DOCX (including tables), TXT and Markdown |
| `db.py` | SQLite schema, versioned migrations and queries |
| `assistant.py` | The Assistant tab (kept from before the pivot) |
| `static/` | Vanilla HTML/CSS/JS single-page UI, no CDN or build step |

### 2.2 Agent (`agent/`)

A small Python process (httpx, psutil, python-dotenv) on each member's computer. It needs no Docker and opens no listening port.

- **Sprint 1:** read the model's capabilities from the local Ollama (`/api/show`) and the computer's resources, then register with the master, retrying with growing delays (2 → 60 s) until the master is reachable. Wrong token, unknown model or wrong master URL stop the agent with a clear message.
- **Sprint 2 (planned):** periodic heartbeat with status.
- **Sprint 3 (planned):** pull tasks from the master, run them with the local model, return results.

### 2.3 Assistant and LiteLLM gateway

The chat assistant from before the pivot stays as a secondary tab. It reaches the models through a LiteLLM gateway. In Sprint 3 it moves onto the agent infrastructure and the gateway is removed (PB-36, PB-37).

## 3. Deployment

| Where | What runs | How |
|---|---|---|
| Master computer (İshak) | master, LiteLLM gateway, `uye1` agent, Ollama | `docker compose up -d --build`; Ollama on the host |
| Master computer, temporarily | `uye2`–`uye6` agents with local copies of the members' models | `docker compose --profile staging up -d` |
| Each member's computer | agent + Ollama (+ Tailscale) | `agent-node/setup.ps1` or `setup.sh`, then `start-agent` |

- **Networking.** Members work from home, so the computers join a private Tailscale network. Members' devices join with a reusable auth key generated by the master's owner and do not need their own Tailscale accounts. The master is reached as `http://<master-device-name>:8000`.
- **Staging honesty.** Staging agents register with `mode=staging` and the UI labels them "Staging · İshak'ın bilgisayarı". When a member's own agent connects, the matching staging container is stopped so both do not register with the same id.
- **Runtime reporting.** Agents report `runtime=docker` or `native`. For Docker agents, the RAM/CPU/OS values describe the Docker VM, and the UI says so.
- **Docker Desktop on the master computer.** Docker Desktop left undeletable socket files after unclean shutdowns and then crashed on start. `scripts/start-docker.ps1` moves those folders aside and starts Docker.

## 4. Data model (SQLite, schema version 2)

```
agents(agent_id PK, member_name, model, mode, runtime, hostname, os, cpu_count, ram_gb,
       model_family, parameter_size, quantization, context_length, capabilities JSON,
       agent_version, registered_at, last_seen_at)

projects(id PK, name, source_filename, document, status[analyzing|decomposed|failed], error,
         spec JSON, analysis_model, analysis_seconds, chunk_count, created_at, updated_at)

tasks(id PK, project_id FK→projects ON DELETE CASCADE, key "T1…", stage, type, title,
      description, details JSON, status[done|planned], performed_by)

task_dependencies(task_id FK→tasks, depends_on_task_id FK→tasks)   -- edges of the DAG
```

Migrations are kept in `db.MIGRATIONS` and applied at start-up. Example: v1 → v2 added `agents.runtime`.

## 5. Master ↔ agent protocol

All calls go from the agent to the master (pull model). Every agent request carries `Authorization: Bearer <AGENT_TOKEN>`, and the master compares tokens in constant time.

### 5.1 Registration (Sprint 1, implemented)

```
POST /api/agents/register
{
  "agent_id": "uye2", "member_name": "Zeynep Duru Küçük", "model": "phi4-mini",
  "mode": "node", "runtime": "native", "hostname": "...", "os": "Windows 11",
  "cpu_count": 8, "ram_gb": 15.8,
  "model_family": "phi3", "parameter_size": "3.8B", "quantization": "Q4_K_M",
  "context_length": 131072, "capabilities": ["completion", "tools"],
  "agent_version": "0.1.0"
}
→ 200 agent record (upsert; registered_at keeps the first registration)
→ 401 wrong token · 422 invalid data · 503 master has no AGENT_TOKEN configured
```

### 5.2 Heartbeat (Sprint 2, planned)

`POST /api/agents/{id}/heartbeat {status: idle|busy, current_task}` every ~10 s. The master marks an agent offline after ~3 missed heartbeats.

### 5.3 Task pull and result (Sprint 3, planned)

- `GET /api/agents/{id}/tasks/next?wait=25`: long poll. The response is either a task with a lease deadline or `204` when there is no work.
- `POST /api/tasks/{task_id}/result {status, files[], log, tokens_per_second}`
- A task whose lease expires without a result is treated as failed and becomes eligible for retry and reassignment (Sprint 4).

## 6. Requirements analysis and decomposition (Sprint 1)

1. **Input.** Pasted text or an uploaded PDF/DOCX/TXT/MD file (≤ 5 MB, ≤ 300,000 characters), normalised. There is no longer an 8,000-character cut.
2. **Sizing.**
   - Tokens are estimated as characters / 3 (errs on the large side for Turkish and English).
   - The context window is the smallest power of two ≥ 8192 that fits prompt + answer, capped at `NUM_CTX_MAX` (32,768 by default) to protect RAM on CPU machines.
   - Longer documents are split at paragraph boundaries into parts that fit.
3. **Extraction.** Each part goes to the master's model, Qwen3.5 4B:
   - `format` = JSON schema of `RequirementsSpec`
   - `temperature 0`, `think: false`
   - The prompt forbids invented features. It asks for open questions instead of guesses, and for answers in the document's language.
   - Output that does not validate is retried once with the validation errors, then the project fails with a message.
4. **Merge.** Partial specs are merged in code. Entities are matched by name (ignoring case, spacing and Turkish diacritics), endpoints by method + path, pages by name, and lists are de-duplicated.
5. **Task graph.** Deterministic templates:
   - T1 requirements analysis — done by the master.
   - Database schema — depends on T1.
   - Backend tasks per group of ≤ 2 entities with their endpoints — depend on the database task. Endpoints are matched to entities by their `entity` field or their path; unmatched endpoints form an extra task.
   - Frontend tasks per group of ≤ 2 pages — depend on T1.
   - Testing and code review — depend on all backend and frontend tasks.
   - Integration, then documentation.
   - Each task's `stage` is its longest-path layer, used for the graph layout and to show which tasks can run in parallel.

## 7. Capability evaluation and agent selection *(planned, Sprint 2)*

- **Benchmarks.** Each dimension is normalised to 0–100 and stored with history:
  - **coding:** small programming problems whose generated code is checked by unit tests in the sandbox
  - **reasoning:** logic and arithmetic questions with known answers
  - **context:** the model's maximum context plus a needle-in-a-haystack test at medium length
  - **speed:** tokens/s
  - **structured output:** share of valid JSON answers
  - **vision:** flag from Ollama
- **Task classification.** Each task type has a weight vector over these dimensions, for example backend = coding 0.6, reasoning 0.2, context 0.2. The team finalises the weights at Sprint 2 Planning.
- **Selection score.**

  ```
  score(agent, task) = Σ weight_i × capability_i
                       − context_penalty (task input larger than the agent's context window)
                       − load_penalty (agent busy)
                       + reliability_bonus (past success rate)
  ```

  Offline agents are excluded. The winning agent and the full score breakdown are stored with the assignment and shown in the UI.

## 8. Security

- **Secrets.** `AGENT_TOKEN` and `LITELLM_MASTER_KEY` live in `.env` files that are never committed. The Tailscale auth key is shared privately.
- **Agents.** No listening ports. Members' Ollama listens on localhost only.
- **Master computer.** Ollama currently listens on all interfaces so containers can reach it. PB-37 revisits this once LiteLLM is removed.
- **Web UI.** No authentication in Sprint 1; it is reachable on the master's LAN and tailnet. Hardening is PB-56.
- **Model output.** Treated as untrusted. The UI inserts it as text, and SVG in assistant answers is sanitised. Generated code will only be executed in a network-less sandbox (Sprint 4).

## 9. Decision records

| # | Decision | Reason |
|---|---|---|
| D1 | 100% local inference with Ollama; no cloud LLM APIs | Data privacy requirement of the team |
| D2 | Pull model: agents call the master, never the reverse | Members are behind home NAT; no ports or firewall rules on their computers; Ollama stays on localhost |
| D3 | Tailscale for connecting homes | Free for up to 6 users; WireGuard end-to-end encryption; chosen by the team over ZeroTier and port forwarding |
| D4 | Master analyses documents with its own model (Qwen3.5 4B) | The course document assigns decomposition to the master; this model has the largest context window (262,144 tokens) |
| D5 | Ollama native API for analysis, LiteLLM kept only for the Assistant | Reliable JSON-schema output, `num_ctx` and `think` control; the gateway goes away in Sprint 3 |
| D6 | Deterministic task graph from an LLM-extracted spec | A 4B model reliably extracts facts; letting code build the graph guarantees a valid DAG |
| D7 | SQLite, stdlib `sqlite3`, versioned migrations | One master process; no extra services |
| D8 | Vanilla JS UI without CDN | Works fully offline; no build tooling to maintain |
| D9 | Staging profile with explicit `mode=staging` labels | Demo and development before members connect, without misrepresenting where agents run |
